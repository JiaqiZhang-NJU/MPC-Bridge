# 清晰度与缓存开发构建

2026-10-11。本地开发构建在 MPC-BE 的选流和播放图之外增加菜单、WinHTTP 请求与本机缓存桥，复用 Bento4 读取 MP4 时间索引，解码和渲染仍使用原播放器。公开发布版本仍为 `0.1.0-preview.4`。本记录不表示全部发布门槛已经通过。

## 使用

打开在线视频后，从顶层或右键「清晰度」菜单选 1080p、720p 等高度。可选项来自本次解析结果；账号限定的格式不会因该菜单而解锁。同高度优先使用在线服务设置的编码、帧率和 HDR 偏好；「更多格式」显示具体格式 ID。「按默认设置」恢复全局最高高度规则。手动选择不覆盖全局设置。

从同一菜单打开「缓存与预加载设置」。默认开启、前方 30 秒、保留后方 15 秒、单视频 256 MiB。倍速增加前方媒体秒数，最高 120 秒；容量优先于秒数目标。配置修改在下次打开在线视频时生效，清理按钮立即清理当前会话数据。

默认目录为 `%LOCALAPPDATA%\MPC-Bridge\Cache`。每次播放使用独立随机会话目录，关闭视频时移除；切换清晰度可暂时保留旧表示供回退。磁盘上限合计计算所有清晰度及音视频，不是每条流各 256 MiB。同一缓存根目录的并发播放器采用保守配额预约，总预算 1 GiB；自定义不同目录分别计算。只清理由本程序标记的会话目录。

信息栏显示音视频共同覆盖的前方缓存秒数，进度条底部显示蓝色缓存带。无法建立完整时间索引时仅显示已缓存字节与「时长未知」，不会按平均码率估算秒数。MP4 样本表、尾部 moov 和单个完整、安全 SAP 的 sidx 已支持；复杂碎片布局不保证准确时间预加载。HLS、直播和非 MP4 沿用原生读取。

媒体请求使用解析结果的 User-Agent 和 Referer，沿用 Windows 代理配置，校验 TLS 与 Range 响应，最多两个上游并发请求。失败块不写成命中；前台读取优先于预取。已加载播放中的缓存失败会尝试以原生读取恢复当前清晰度及播放状态。

## 验证

独立核心检查为原有 148 项，加 28 项缓存/清晰度模型检查。受控网络测试覆盖随机范围逐字节比较、开尾/后缀 Range、416、非法范围和路由、重复请求、容量、冷/热命中、错误 200/Content-Range、ETag 变化、截断响应、慢请求取消与会话清理。MP4 测试包括普通/尾部 moov、SIDX、缺失安全索引、空 SIDX 和超大样本声明。

实际原生播放器受控用例使用已知 MP4 视频与独立 AAC 音频，测试菜单唯一性、最后选择生效、失败回退、暂停/1.5 倍速/音量/静音恢复、设置保存、关闭和正常退出。该用例的 1080/720/480 标签用于测试菜单选择，底层文件为 360p；真实高度另外用公开视频验证，不把标签当成 HD 解码证据。

受控测试在 1.5 倍速证明共同覆盖至少 45 秒、在 3 倍速证明至少 90 秒后，分别中断源服务器 5 秒；播放位置均继续前进。暂停达到目标后没有新增媒体请求。跨进程设置测试使用 Windows 要求的 WM_SETTEXT/WM_GETTEXT，读取实际控件内容再验证 INI 写入和正常退出后的持久化。

dev.2 增加开始切换后立即关闭的回归：缓存归零、清晰度菜单清空、取消请求不会重新打开视频，播放器正常退出。该用例暴露并修复了取消加载期间 UI 与图线程的同步控件调用互相等待。完整受控播放结果见本地 `quality-cache-dev2-uiwait-playback.log`，最终缓存网络回归见 `cache-dev2-final-integration.log`。

公网实测三例：

| 样例 | 实际播放与清晰度切换 |
| --- | --- |
| `BV13x41117TL`，约 554 秒 | 1080p → 720p → 1080p；原有长按 3 倍速及恢复回归通过 |
| `BV1bK411W797`，分集首段 | 720p → 480p → 720p；切换后位置继续前进 |
| `BV1vL411G7N7` | 1080p → 720p → 1080p；切换后位置继续前进 |

这些公共样例取自 [yt-dlp 的 Bilibili 测试列表](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/bilibili.py)，验证使用随包固定版本解析器，不使用账号或 Cookies。当前 YouTube 样例能解析格式，但播放器位置没有继续前进，未通过本机播放验证；尚不能保证此次缓存接入解决其网络访问问题。

受控 HTTP 性能记录：固定 1 MiB 范围、2 MiB/s、20 ms 请求延迟，各条件 10 次。直接读取中位数 557.986 ms，冷缓存 605.770 ms，热缓存 25.617 ms；10 次热读取上游请求均为零。CSV 与 JSON 在本地 `_bin/bridge/cache-performance/`。这衡量 HTTP 字节交付，尚不证明画面首帧或播放器跳转性能满足计划目标。

## 尚未通过的发布门槛

签名媒体地址失效后的自动重新解析尚未实现；需要重新打开网页链接。现有失败回退不会刷新旧签名，也不能跨新地址盲目复用缓存。缓存图初次打开阶段的所有超时/写盘故障组合还需扩大验证。

计划中的原生首帧/暖缓存跳转各 10 次对比、缓存新增内存预算、音画同步测量、磁盘故障压力、异常残留压力和不同 DPI/全屏的人工回归尚未完成。代理目前沿用 Windows 配置，未提供单独代理选择。音轨、字幕恢复代码已接入，但多轨道切换还缺少完整实测。

因此这次交付为本地开发构建，不能把 M4 或全部缓存计划标记为完成，也不会更新公开 Release 链接。
